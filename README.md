# Мониторинг ресурсов как HTTPS-сервис

Капстоун по системному администрированию. Автор: Щебаров Вадим Денисович.
Дорожка: «Продвинутый». Среда: постоянная Ubuntu 22.04.5 LTS в Multipass.

## Что делает проект

`script.sh` три раза с интервалом 5 секунд собирает `free -h`, `df -h` и
`uptime`, добавляя временную метку и результаты в `monitor.log`.
При ошибке команды замера или записи скрипт печатает сообщение в stderr
и завершается с кодом 1. Обычный успешный запуск завершается с кодом 0.
Это конечная серия замеров, а не непрерывный мониторинг или система оповещений.

## Архитектура

```text
Клиент --HTTPS:443--> Nginx на ВМ --HTTP:8080--> контейнер my-app
                                                    |
                                 Python HTTP-сервер + script.sh
                                                    |
                                                monitor.log
```

Nginx завершает TLS и перенаправляет HTTP на HTTPS с кодом 301.
systemd запускает существующий контейнер после Docker и подключает его вывод
к журналу службы. После трёх замеров скрипт завершается, HTTP-сервер продолжает
отдавать созданный лог.

## Файлы

| Файл | Назначение |
| --- | --- |
| `script.sh` | Сбор показателей ресурсов |
| `sample_output.txt` | Реальный пример результатов первоначальных запусков |
| `Dockerfile` | Образ Ubuntu 22.04 со скриптом и Python HTTP-сервером |
| `docker-compose.yml` | Проверенный этап запуска через Compose; конечный сервис управляется systemd |
| `nginx.conf` | Копия конфигурации `/etc/nginx/sites-available/my-app` |
| `my-app.service` | Копия `/etc/systemd/system/my-app.service` |

## Отдельный запуск скрипта на Ubuntu

```bash
chmod +x script.sh
./script.sh
echo $?
cat monitor.log
```

Ожидание завершения — около 15 секунд. Лог создаётся в текущем каталоге
и дополняется при повторных запусках.

## Сборка и проверка настроенного сервиса

```bash
docker build -t my-script .
docker ps -a
sudo nginx -t
sudo systemctl status my-app --no-pager
sudo systemctl is-enabled my-app
curl -kI https://127.0.0.1/monitor.log
curl -k https://127.0.0.1/monitor.log
```

Эти проверки предполагают, что контейнер, Nginx, сертификат и служба уже
настроены на ВМ. Сборка образа сама по себе не создаёт и не обновляет
существующий контейнер. При первоначальной настройке контейнер подготовлен
командой `docker create -p 8080:8080 --name my-app my-script`, затем запущен
через `sudo systemctl start my-app`.

`-k` используется только для локального учебного самоподписанного сертификата:
проверка доверия и имени отключена. TLS-ключ хранится на ВМ в
`/etc/ssl/private/my-app.key`, сертификат — в `/etc/ssl/certs/my-app.crt`.
Приватные ключи в репозиторий не включаются.

## Журналы

```bash
sudo journalctl -u my-app -n 20 --no-pager
sudo tail -n 20 /var/log/nginx/access.log
sudo tail -n 20 /var/log/nginx/error.log
```

После тестового запроса запись о `/monitor.log` видна в журнале HTTP-сервера
через journald и в журнале Nginx. Время внутри контейнера показано в UTC,
время ВМ — MSK (UTC+3).

## Учебное хранилище

На этой же ВМ созданы три файла-диска по 512 МиБ в `/mnt/raid-lab`.
Первые два объединены в RAID 1 `/dev/md0`, ext4 смонтирована в `/mnt/raid`.
На третьем устройстве создана группа LVM `vg_data` и логический том
`lv_logs` размером 200 МиБ, смонтированный в `/mnt/logs`.

```bash
cat /proc/mdstat
sudo lvs
sudo vgs
df -h /mnt/raid /mnt/logs
```

RAID и LVM демонстрируют разные задачи и здесь созданы отдельно:
зеркалирование и гибкое выделение пространства. Это файлы на одном диске,
поэтому они не защищают от физического отказа этого диска. Лог контейнера
не перенесён на эти тома. Привязки loop-устройств и монтирование после
перезагрузки восстанавливаются отдельно; повторное форматирование не требуется.

## Ограничения учебного решения

- HTTP-сервер публикует готовые файлы без аутентификации.
- `monitor.log` находится в записываемом слое контейнера и исчезает при его удалении.
- systemd отслеживает контейнер с HTTP-сервером, а не отдельно фоновый скрипт.
- Порт 8080 опубликован на интерфейсах ВМ; ограничение его только loopback не настроено.
- Автозапуск службы включён; отдельный контроль после перезагрузки не выполнялся.
- Автоматического развёртывания всей среды с нуля (`bootstrap.sh`) нет:
  на постоянной ВМ использован ручной прогон по требованиям выбранной дорожки.
